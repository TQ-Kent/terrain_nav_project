# Session notes 2026-10-19: Unity stalls, tight gaps and the 35 s goal

Branch `feature/speed-governor`, nothing committed. This is the record of one long working session on the
Unity maze run (Smac2D + RPP, `localization:=ground_truth`, maze seed 42, goal (10, -10)). Read it before
changing the Nav2, Collision Monitor or explorer settings again.

## 1. Where it ended up

- **Reliable setup found:** the profile `reliable` (section 5) reached the goal in **5 of 5** valid Unity runs at
  0.8 m/s: 34.63, 45.50, 46.98, 48.00 and 60.97 s (median 47.0 s). It is reliable at *reaching* the goal, not at
  reaching it in 35 s. The key change is the RPP look-ahead of 0.35 m (default 0.6 m): the same setup with 0.6 m was
  stuck at the gap for the whole 90 s run. One maze (seed 42), 5 runs: an indication, not a guarantee.

- **Goal given:** the robot should reach the goal in 35 s or less (runs are capped with
  `exploration.max_time=35`; the clock starts when the first goal is sent).
- **Result:** at 1.0 m/s with `goal_weight` 2.0 (section 5 settings, three variants) 4 of 12 capped runs reached the goal
  inside 35 s: 34.72 s (no reverse zone), 34.0 s and 31.75 s (with the reverse zone), 27.15 s (with the reverse zone
  and `progress_time` 4). With the reverse zone it is 3 of 8. No setting reached 35 s reliably. Most failures lose
  10-20 s at one tight gap or in the bottom-left corridor (section 3). Sample sizes are 4 runs per setting, so treat
  every comparison below as an indication, not a measured rate.
- **Replanning time was not the problem** (section 2).
- **Last idea tried** (planner path further from the wall, section 5): 0 of 4 reached, but one run ended 0.7 m short.
  It is not adopted as a recommendation; it is an opt-in setting.

## 3. What actually stalls the robot (with evidence)

All numbers come from `tools/halt_analysis.py` recordings (section 7). The raw logs are in
`docs/results/runs_2026-10-19.tar.gz`.

| # | Failure | Evidence | Status |
|---|---|---|---|
| 1 | **Tight gap closed by the costmap** (a ~0.52 m gap at about (2.0, -2.8) between two wall ends) | the circle `robot_radius` 0.22 m plus lidar wall thickness leaves too little room; plans fail with `no valid path found` | fixed by a smaller circle (0.17 m), see section 4 |
| 2 | **Rectangle footprint refused by RPP** | Nav2 takes the inscribed radius from the *shortest* footprint edge from the origin (0.089 m at the front), so the sides need `2 * (half width + 0.089)` = 0.524 m, a few mm more than the gap. | 3 | **Collision Monitor holds the command at 0** (state `APPROACH`, polygon `VelApproach`) | recorder state topic + lidar nearest point: wall point 0.146 m from the axle, inside the 0.15 m disc and inside the 0.153 m wheel reach (robot touching the wall) | reverse zone (below) lets the backup recovery work; the lock still shows up (v4) |
| 4 | **Rotation-in-place jam at the gap** | rear corners sweep ~0.24 m, gap half-width 0.26 m; nearest point 0.222-0.226 m straight behind the robot while commanded +-1.0 rad/s | `use_rotate_to_heading=false` avoids the in-place spin |
| 5 | **RPP `collision ahead` silences** in the bottom-left corridor (about (-0.4..0.5, -5..-6.5)) and at the gap | controller sends exactly 0/0 for 3-17 s while plans keep arriving; the monitor is not involved | not solved; intermittent |
| 6 | **Stop-and-go at every frontier goal** | 9 of 15 goals ended in a full stop; 2-9 s per run in braking plus re-accelerating | `exploration.chain_distance` removes it |
| 8 | **RPP arc cuts the gap corner** (the cause of cases 2 and 5 in the end) | with `lookahead_dist` 0.6 m the robot stayed around the gap for 90 s: 8 silences of 1.5-8.6 s and 172 `collision ahead` with the nearest wall 0.24-0.47 m away, so the rejected arc to the look-ahead point, not the robot, was in collision | fixed by `rpp.lookahead_dist=0.35`, `min_lookahead_dist=0.25` (profile `reliable`) |
| 7 | **Route** | at `goal_weight` 1.0 the explorer went into the dead-end left corridor first (about 12 s detour) | `goal_weight` 2.0 helps |

The original "start-corner wall lock from the Collision Monitor" did occur (one run with the 0.2 m rotation disc,
and again at the gap, case 3), but cases 5 and 6 cost more total time in this session.

## 4. Changes made (all opt-in unless noted)

Config lives in `ros2_ws/src/terrain_nav_bringup/config/maze_test.yaml`; override from the launch line with
`set:=a.b=value,...` (lists cannot go through `set:`).

| Setting | Default | What it does |
|---|---|---|
| `speed.rotation_zone` (m) | 0 (stock `FootprintApproach`) | swaps in Nav2's `velocity_polygon`: a small disc for turning in place, the drive zone for everything else |
| `speed.reverse_zone` | true (only with `rotation_zone`) | rear-only zone while backing up, so a wall at the front or side does not block the backup recovery |
| `costmap.robot_radius` (m) | 0 | plain circle for both costmaps and the monitor; 0.17 = wheel outer face 0.153 m + 0.017 |
| `costmap.drive_zone` (m) | 0.15 | monitor approach disc used with `robot_radius` |
| `costmap.footprint` (`waffle` or list) | none | rectangle from the TurtleBot3 waffle URDF (wheels at +-0.144 m, 0.018 m thick, base box x -0.197..+0.069, 0.02 m padding). Rejected, see case 2 |
| `costmap.inflation_radius`, `cost_scaling_factor` | 0 (keep 0.55 / 3.0) | retune both inflation layers |
| `costmap.planning_radius` | 0 | global-costmap circle while a footprint is set (stalled 6/6, left off) |
| `rpp.<param>` | none | passes any parameter to RPP (`use_rotate_to_heading`, `use_cost_regulated_linear_velocity_scaling`, ...). Numbers take the type of the parameter they replace |
| `planner.<Name>.<param>` | none | same for planners, e.g. `planner.Smac2D.cost_travel_multiplier=4` |
| `exploration.chain_distance` (m) | 0 | within this distance of a frontier target, send the next frontier at once |
| `exploration.recover_timeout` (s) | 0 | drop the current target after no movement or no progress; did not help, left off |
| `tolerance.progress_time` (s) | **2.0 (changed default, Nav2 default is 10)** | time without movement before Nav2 reports failure and starts backup/spin |

Other changes: `visualize: true` on the stock `FootprintApproach` zone (display only, thresholds unchanged);
RViz shows the local footprint and the monitor zones (`/FootprintApproach`, `/VelApproach`);
`tools/halt_analysis.py` records the Collision Monitor state, lidar nearest point, yaw and reads the pose from TF
(Unity has no pose topic), and dumps the local costmap when the controller is silent;
`goal_explorer` result line now has `chained` and `recoveries`.

Unity prefab vs Nav2 (checked, matching): track 0.288 m, wheel radius 0.033 m, lidar 0.064 m behind the axle,
range 0.12-10 m, speed caps 1.0 m/s and 2.0 rad/s. The Unity robot's collision mesh is the waffle base with the
wheels at +-0.153 m.

Files changed this session: `maze_config.py`, `bringup_maze_2d.launch.py`, `maze_test.yaml`,
`nav2_params_maze.yaml` and `nav2_params_2d.yaml` (display flag only), `goal_explorer.py`, `terrain_nav.rviz`,
`tools/halt_analysis.py`, `tools/time_planners.py` (new), docs (this file, `PLANNING_COMPARISON.md`, `CREDITS.md`),
`docs/results/*` (new data), `README.md`.

## 5. Recommended setup and how to run it

```bash
cd ros2_ws && source /opt/ros/jazzy/setup.bash && source install/setup.bash
ros2 launch terrain_nav_bringup bringup_maze_2d.launch.py planner:=Smac2D controller:=RPP profile:=reliable
```

`profile:=reliable` applies the overrides listed under `profiles.reliable` in `maze_test.yaml` (`set:=` still wins):
`speed.max_linear=0.8`, `speed.rotation_zone=0.14`, `costmap.robot_radius=0.17`, `costmap.inflation_radius=0.5`,
`rpp.use_rotate_to_heading=false`, `rpp.use_cost_regulated_linear_velocity_scaling=true`,
`rpp.inflation_cost_scaling_factor=3.0`, `rpp.lookahead_dist=0.35`, `rpp.min_lookahead_dist=0.25`,
`exploration.chain_distance=1.0`, `exploration.goal_weight=2.0`. On top of these defaults apply: `speed.reverse_zone`
true, `tolerance.progress_time` 2.0 s, `costmap.drive_zone` 0.15. Add `exploration.max_time=90` to bound a run.
Unity must be in Play; press Play again (or check the first `Begin navigating` pose is `(0, 0)`) before every run.

For a faster but less reliable setup (about 3 in 8 under 35 s): the same plus `speed.max_linear=1.0`, with the
default look-ahead and `tolerance.progress_time=4` (section 6, "+ progress_time 4 s").

Headless: `headless.robot_radius` (default 0.2) must match `costmap.robot_radius`, otherwise the simulated robot
hits walls the planner thinks are clear. With `profile:=reliable simulator:=headless` and the default 0.2 the run
stalled (73 wall contacts); with `set:=headless.robot_radius=0.17` it reached the goal in 69.2 s (17 wall contacts).

Tried last and **not** recommended yet: `costmap.inflation_radius=0.8` with
`planner.Smac2D.cost_travel_multiplier=4`, to keep the path further from walls.

## 7. Tools and how to use them

- **Run and record** (the recorder does not stop with the launch, so give it a `timeout` and kill leftovers by
  PID with SIGINT):
  ```bash
  ros2 launch terrain_nav_bringup bringup_maze_2d.launch.py ... > /tmp/run.log 2>&1 &
  sleep 12; timeout 85 python3 tools/halt_analysis.py record /tmp/run
  python3 tools/halt_analysis.py analyze /tmp/run
  ```
  `analyze` splits the run into moving / slow / halted by cause and prints which Collision Monitor zone held the
  command at 0. Samples: `<prefix>_samples.csv` (pose, yaw, three command stages, monitor state, nearest lidar
  point); events: `<prefix>_events.csv`.
- **Planner timing:** `python3 tools/time_planners.py 100` against a running headless stack.
- **Raw data:** `docs/results/runs_2026-10-19.tar.gz` (logs, recordings, stall dumps, plots) and
  `docs/results/governor_logs.tar.gz` (earlier governor runs).

## 8. Gotchas

- Never `pkill -f` from the tool shell (it kills the shell). Never run two stacks on one `ROS_DOMAIN_ID`.
- Unity does not always reset the robot between runs. Check the first `Begin navigating` pose is `(0, 0)`.
- Do not save C# scripts while Unity is in Play.
- A numeric override is parsed as int by YAML; Nav2 rejects an int for a double parameter and the whole bringup
  aborts (fixed for `rpp.*` and `planner.*`; other keys may still need `4.0` instead of `4`).
- A run that starts off the origin (Unity did not reset) is invalid; discard it and restart Play.
- The recorder's `slow time split` can print a negative value when the recording runs long past the goal.
